Grammar Development Guide

Overview

The generic compiler is fully data-driven: the language it parses is described in a plain JSON grammar configuration object. No JavaScript modifications are needed to define a new language or extend an existing one — only the configuration changes.

A grammar configuration has three top-level sections:
 1. {
 2.   "grammar": { /* language identity */ },
 3.   "engineConfig": { /* tokenization + compilation rules */ },
 4.   "logging": { /* log level */ }
 5. }

The grammar section

Identifies the language. The rootRule names the compilation rule that matches the top-level program structure.
 1. "grammar": {
 2.   "name": "MY_LANG",
 3.   "version": "1.0.0",
 4.   "rootRule": "INSTRUCTION_SEQUENCE"
 5. }

The engineConfig section

Contains two arrays: tokenizationRules and compilationRules. It may also contain an input sub-object for tokenizer configuration (e.g. comment patterns, whitespace handling).

Tokenization rules

The tokenizer reads the source left-to-right, attempting to match each character position against the declared rules. The rule with the highest priority wins when multiple rules can start with the same character. Three rule types are available:

FIXED_CHAR

Matches a single fixed character. Used for punctuation and operators.
 1. {
 2.   "name": "SEMICOLON",
 3.   "type": "FIXED_CHAR",
 4.   "value": ";",
 5.   "priority": 5
 6. }

FIXED_VALUE

Matches one of a fixed set of multi-character strings. Used for keywords and boolean literals. Must have a higher priority than SEQUENCE rules that share the same start characters (e.g. keywords vs. identifiers).
 1. {
 2.   "name": "KEYWORD",
 3.   "type": "FIXED_VALUE",
 4.   "values": [ "if", "else", "while", "for", "function", "return", "var", "const" ],
 5.   "priority": 10
 6. }

SEQUENCE

Matches a run of characters based on allowed character sets. Optionally enforces a start character set, an end character, and a custom validator function name.
FieldRequiredDescription
allowedCharsyesCharacters that may appear anywhere in the sequence.
startsWithnoRestricts the first character to this set. Defaults to allowedChars.
endsWithnoFixed terminator character (e.g. " for string literals).
validatornoName of a built-in validator to apply to the token value after matching (e.g. "numberValidator").
 1. { // identifier
 2.   "name": "IDENTIFIER",
 3.   "type": "SEQUENCE",
 4.   "allowedChars": "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789_",
 5.   "startsWith": "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ_",
 6.   "priority": 7
 7. }

 1. { // string literal
 2.   "name": "CHAR_SEQUENCE",
 3.   "type": "SEQUENCE",
 4.   "allowedChars": "*",
 5.   "startsWith": "\"",
 6.   "endsWith": "\"",
 7.   "priority": 6
 8. }
Priority guidelines:
Token typeRecommended priority
Keywords, boolean, null10
Multi-char operators (++, --, != …)8–9
Identifiers, numbers7
String literals6
Single-char punctuation5

Compilation rules

Compilation rules define the grammar of the language. Each rule has a name and an inner rule object. The syntax analyser starts from the rootRule and recursively tries to match the token stream.

Rule types

TypeKeyMeaning
logic + $andArray of sub-rulesAll sub-rules must match in order. Produces an AND node in the execution tree.
logic + $orArray of sub-rulesFirst matching sub-rule wins. Produces an OR node. Order matters: put more specific alternatives first.
tokenname (+ optional value)Matches a single token of the given type. An optional value field restricts to a specific lexical value (e.g. keyword "if").
rulenameReferences another top-level compilation rule.

Example: variable declaration

 1. {
 2.   "name": "VAR_DECL",
 3.   "rule": {
 4.     "type": "logic",
 5.     "$and": [
 6.       { "type": "token", "name": "KEYWORD", "value": "var" },
 7.       { "type": "token", "name": "IDENTIFIER" },
 8.       { "type": "token", "name": "SEMICOLON" }
 9.     ]
10.   }
11. }

Example: if / else statement

 1. {
 2.   "name": "IF_STATEMENT",
 3.   "rule": {
 4.     "type": "logic",
 5.     "$or": [
 6.       { /* if + else variant — more specific, must come first */
 7.         "type": "logic", "$and": [
 8.           { "type": "token", "name": "KEYWORD", "value": "if" },
 9.           { "type": "rule", "name": "CONDITION" },
10.           { "type": "rule", "name": "BLOCK" },
11.           { "type": "token", "name": "KEYWORD", "value": "else" },
12.           { "type": "rule", "name": "BLOCK" }
13.         ]
14.       },
15.       { /* if only */
16.         "type": "logic", "$and": [
17.           { "type": "token", "name": "KEYWORD", "value": "if" },
18.           { "type": "rule", "name": "CONDITION" },
19.           { "type": "rule", "name": "BLOCK" }
20.         ]
21.       }
22.     ]
23.   }
24. }

Versioning your grammar

The recommended workflow when extending a language is:
  1. Copy the current compilerConfig_vX.Y.Z.json to compilerConfig_vX.Y.(Z+1).json
  2. Increment the grammar.version field inside the new file
  3. Add or modify tokenization and/or compilation rules
  4. Add the corresponding handler in the language runtime plugin (see Execution Engine Development Guide)
  5. Add regression test cases in workDir/tests/ and run the test suite
Never modify an existing grammar config file that is already in production use. Always create a new version file and update the reference in the consumer plugin.

Common pitfalls

SymptomCause
Keyword is tokenized as IDENTIFIERThe FIXED_VALUE rule for the keyword has a lower priority than the SEQUENCE rule for IDENTIFIER. Raise the FIXED_VALUE priority to at least 10.
More specific $or alternative never matchesA more general alternative appears earlier in the $or array. Move the specific alternative first.
Multi-char operator (e.g. !=) is tokenized as two separate tokensThe FIXED_CHAR rule for ! fires before the FIXED_VALUE rule for !=. Raise the priority of the multi-char rule above the single-char one.
Compilation fails silently with no error detailSet the logging level to debug in the grammar config logging section for detailed analyser output.
