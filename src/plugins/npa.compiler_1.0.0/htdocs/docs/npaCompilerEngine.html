Execution Engine Development Guide

Overview

After compilation, the source program is represented as a tree of ExecutionUnit (EU) nodes. The ExecutionEngine walks this tree in order and delegates each node to a language runtime plugin that you provide. This guide explains the EU node structure, the EuReader navigation API, the engine memory model, and the full pattern for writing a runtime plugin.

ExecutionUnit node structure

Every node in the compiled tree is an ExecutionUnit object with three fields:
FieldTypeMeaning
namestringRule or token type (e.g. "IF_STATEMENT", "AND", "IDENTIFIER").
tokenobjectSource token with .value, .line, .char.
nextEU or EU[]Single child for named/OR nodes; array of children for AND nodes; token value for leaf nodes.
Key invariants:
  • Named rule node — eu.next is a single EU (the matched alternative). The rule name is eu.name.
  • AND node — eu.name === "AND", eu.next is an ExecutionUnit[] of the matched sub-rules in order.
  • Token leaf — eu.name is the token type, eu.token.value (also eu.value) holds the lexical value.

EuReader — navigation API

Never traverse raw .next.next[n] chains directly. Use the EuReader wrapper (defined at the top of language runtime plugin files) to navigate the tree safely:
 1. // wrapping and unwrapping
 2. r(eu) // wrap an EU into an EuReader
 3. r(eu).eu // unwrap back to the raw EU

 4. // navigation on a NAMED node (eu.next = single child)
 5. r(eu).inner() // EuReader wrapping eu.next
 6. r(eu).innerName() // eu.next.name

 7. // navigation when the named node's child is an AND node (eu.next.next = array)
 8. r(eu).child(n) // EuReader wrapping eu.next.next[n]
 9. r(eu).childName(n) // eu.next.next[n].name
10. r(eu).childValue(n) // eu.next.next[n].value

11. // navigation when eu IS the AND node (eu.next = array)
12. r(eu).item(n) // EuReader wrapping eu.next[n]
13. r(eu).itemName(n) // eu.next[n].name
14. r(eu).itemValue(n) // eu.next[n].value
15. r(eu).firstChild() // EuReader wrapping eu.next[0]
Rule of thumb:
  • After r(instruction).inner() you are on the AND node → use .item() / .itemValue()
  • When you stay on a named node → use .child() / .childValue()

Engine memory model

The execution engine manages variables through a namespace stack. A namespace is a plain JavaScript object mapping variable names to values. The stack supports lexical scoping: variable lookups walk the stack from top (innermost) to bottom (global scope).
MethodDescription
engine.sto(name, value)Store value under name in the current (top) namespace.
engine.rcl(name)Recall a variable: searches from top namespace down to the root namespace.
engine.push(ns)Push a new namespace (creates a new scope). Pass a string label for debugging.
engine.pop()Pop the current namespace and discard its variables.
engine.rfc(name, fn, async)Register a native JS built-in function. Set async to true for async functions.
engine.dcl(name, eu)Declare a compiled function by name (stores its EU subtree).
engine.cal(name, args)Call a built-in or declared function by name.
engine.halt(msg)Raise the halt flag with an error message. Execution stops immediately.
Scoping conventions:
  • for and while loop bodies do not push a namespace — variables modified inside a loop are visible after the loop (JavaScript semantics).
  • Function calls do push a namespace (via engine.cal), creating proper function-level scope.

Writing a language runtime plugin

A runtime plugin is a plain JavaScript object with three mandatory methods:
MethodSignatureDescription
processprocess(eu, engine)Called for each ExecutionUnit node. Dispatches to per-instruction handlers.
callFunctioncallFunction(name, args, engine)Called when the engine encounters a function call. Looks up and executes the named function.
halthalt(msg, engine)Called when an unrecoverable error occurs. Should call engine.halt(msg).

Dispatch pattern

The standard dispatch pattern inside process() unwraps the top-level named node and routes to a dedicated handler based on the matched rule name:
 1. process(eu, engine) {
 2.   let instruction = r(eu).inner().eu; // unwrap: named → AND node
 3.   switch(instruction.name) {
 4.     case 'VAR_DECL': this.processVarDecl(r(instruction).inner().eu, engine); break;
 5.     case 'IF_STATEMENT': this.processIfStatement(r(instruction).inner().eu, engine); break;
 6.     default:
 7.       engine.halt('Unknown instruction: ' + instruction.name);
 8.   }
 9. }

Handler pattern

Each handler receives an EU that is already the AND node of the matched rule. Use .item(n) to access children by index:
 1. processVarDecl(instruction, engine) {
 2.   // rule: KEYWORD("var") IDENTIFIER SEMICOLON
 3.   let eu = r(instruction);
 4.   let varName = eu.itemValue(1); // index 1 = IDENTIFIER token
 5.   engine.sto(varName, undefined);
 6. }

Evaluating expressions

For nodes that produce a value (arithmetic, comparisons, function calls …), use an EvaluationTree helper that recursively resolves the expression tree:
 1. processAssignment(instruction, engine) {
 2.   // rule: IDENTIFIER ASSIGN_OP EXPRESSION SEMICOLON
 3.   let eu = r(instruction);
 4.   let varName = eu.itemValue(0);
 5.   let exprNode = eu.item(2).eu;
 6.   let value = new EvaluationTree(exprNode, engine).evaluate();
 7.   engine.sto(varName, value);
 8. }
Inside EvaluationTree.evaluate(), add a case for each new expression leaf type:
 1. // inside EvaluationTree.evaluate()
 2. if ('MY_LITERAL' == expr.name) {
 3.   this.value = parseMyLiteral(expr.token.value);
 4. }

Adding a new instruction type — checklist

  1. Add tokenization rules (if the new syntax needs new token types) and compilation rules to the grammar config (see Grammar Development Guide).
  2. Add a process<InstructionName>(instruction, engine) method to the runtime plugin.
  3. Add a dispatch case in process() for the new rule name.
  4. If the new instruction evaluates an expression, add the corresponding case in EvaluationTree.evaluate().
  5. Write a test case in workDir/tests/ and verify that all existing tests still pass.

Async built-in functions

When a built-in registered with async: true is called, the engine increments an internal _pendingCallbacks counter. The execution loop waits for all pending callbacks to complete before considering execution finished. Declare async built-ins as:
 1. let builtins = {
 2.   fetchData: {
 3.     fn: async (args) => {
 4.       let data = await someAsyncCall(args[0]);
 5.       return data;
 6.     },
 7.     async: true
 8.   }
 9. };
The memory space snapshot is taken after all pending callbacks resolve, so async built-in results stored via engine.sto() are visible in result.memorySpace.
