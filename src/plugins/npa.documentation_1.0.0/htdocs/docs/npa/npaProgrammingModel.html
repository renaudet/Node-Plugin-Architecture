NPA — Programming Model

Overview

NPA (Node Plugin Architecture) is a lightweight plugin framework for Node.js. It provides a structured way to decompose a server application into independently declared, versioned, and dependency-managed plugins that are discovered and wired together at startup by a central Integration Runtime.

The three fundamental concepts are:
  • Plugins — self-contained units of code described by a manifest.json
  • Extension Points — named hooks that plugins provide for others to extend
  • Sites — filesystem directories scanned by the runtime to discover plugins

The Plugin

Every NPA plugin lives in its own directory and consists of two files:
  • manifest.json — declarative metadata: id, version, dependencies, extensions
  • plugin.js — the implementation, a singleton module exporting a Plugin instance
A minimal plugin looks like this:
 1. // my.plugin_1.0.0/plugin.js
 2. const Plugin = require('../../core/plugin.js');
 3. var plugin = new Plugin();
 4. 
 5. plugin.onConfigurationLoaded = function() {
 6.   // called once the plugin is fully wired and ready
 7.   this.info('My plugin is running!');
 8. };
 9. 
10. module.exports = plugin;
Plugins are singletons — the same module instance is reused for the lifetime of the process. The base Plugin class provides logging, service access, configuration reading, and state management.

The manifest.json

The manifest is the contract of a plugin. It declares everything the runtime needs to load, sort, and wire plugins correctly.
 1. {
 2.   "id": "my.plugin",
 3.   "name": "My Plugin",
 4.   "version": "1.0.0",
 5.   "plugin": "plugin.js",
 6.   "requires": [
 7.     { "type": "plugin", "id": "npa.core", "version": "1.0.0" },
 8.     { "type": "plugin", "id": "npa.logging", "version": "1.0.0" }
 9.   ],
10.   "extends": [
11.     {
12.       "point": "npa.log.provider",
13.       "id": "my.plugin.logger",
14.       "dir": "my.plugin"
15.     }
16.   ],
17.   "provides": [
18.     { "id": "my.extension.point" }
19.   ]
20. }

Key fields

  • id — unique plugin identifier, used as the key in the runtime map
  • version — semver string; when multiple versions of the same plugin are found, the highest wins
  • plugin — relative path to the implementation module
  • requires — explicit hard dependencies; the runtime will refuse to load this plugin if any are unresolved
  • extends — contributions to extension points of other plugins; each entry must have a point (the extension point id) and a unique id
  • provides — extension points this plugin declares and owns
Important: the extends array must never end with a trailing comma — manifest.json is parsed with require() which uses strict JSON. A trailing comma will silently drop the entire plugin from the runtime.

Explicit Dependency Declaration

NPA uses a weight-based topological sort to determine plugin load order. Each plugin's weight is computed recursively from its requires graph: a plugin with no dependencies has weight 1; each dependency adds 10× its own weight. Plugins are then loaded in ascending weight order, guaranteeing that every dependency is initialized before the plugin that needs it.

The resolution algorithm:
  1. Scan all sites and parse every manifest.json
  2. For each plugin, verify that all requires entries resolve to a known plugin id — if any is missing, the plugin is marked unresolved and excluded from loading
  3. Compute weights and sort
  4. Load plugins in order: require(plugin.js) → configure() → beforeExtensionPlugged() → lazzyPlug() calls → onConfigurationLoaded()
Rule: if plugin A must be initialized before plugin B, B must list A in its requires. Do not rely on discovery order — it is filesystem-dependent and not guaranteed.

Circular dependency warning

The weight computation is recursive with no cycle guard. A circular dependency in requires (A → B → A) will cause a RangeError: Maximum call stack size exceeded crash at startup. If a plugin needs to contribute to another plugin but must not create a hard dependency cycle, use extends only — the lazzyPlug() mechanism fires without adding to the weight graph.

Extension Points and lazzyPlug

An extension point is a named hook declared in a plugin's provides array. When another plugin contributes to it via extends, the runtime calls lazzyPlug(extenderId, extensionConfig) on the provider plugin at load time.

The provider overrides lazzyPlug() to inspect the contribution and register it:
 1. plugin.lazzyPlug = function(extenderId, extensionConfig) {
 2.   if ('my.extension.point' === extensionConfig.point) {
 3.     // extensionConfig is the full object from the contributor's manifest.json
 4.     let contributorPlugin = this.runtime.getPlugin(extenderId);
 5.     this.registeredItems.push({
 6.       label: extensionConfig.label,
 7.       handler: contributorPlugin[extensionConfig.handler]
 8.     });
 9.   }
10. };
Note that lazzyPlug() is called before onConfigurationLoaded() of the provider. If initialization work is needed after all contributions are collected, do it in onConfigurationLoaded().

Lazy Plugin Loading

NPA uses a PluginWrapper to defer the actual require(plugin.js) call until the plugin is first accessed via runtime.getPlugin(id) or plugin.getService(name). This means a plugin's code is only executed when something actually needs it — reducing startup time and avoiding initialization order issues between independently developed plugins.

Services

The npa.core.service extension point allows a plugin to register itself as a named service in the global service registry. Any other plugin can then retrieve it with:
let myService = plugin.getService('my-service-name');
Service registration in manifest.json:
{
  "point": "npa.core.service",
  "id": "my.plugin.service",
  "service": "my-service-name"
}
Services are resolved lazily — the plugin backing the service is only loaded when getService() is first called.

Adding "autostart": true to the extension forces the service to be loaded immediately during application startup, before the application plugin's start() is called — useful for services that must initialize background tasks or listeners early:
{
  "point": "npa.core.service",
  "id": "my.plugin.service",
  "service": "my-service-name",
  "autostart": true
}

Environment Variable Injection

Any string value in manifest.json that starts with $ is treated as an environment variable reference, with an optional default value after a comma:
"port": "$MY_PORT,9080"
Resolved at runtime via plugin.getConfigValue('http.port') (using a dot-path into the manifest JSON). If the environment variable is set, its value is used; otherwise the default is returned. The type can be specified as a second argument: getConfigValue('http.port', 'integer').

Sites and the Site Configuration File

A site is a filesystem directory that the Integration Runtime scans for plugin directories. Every sub-directory inside a site that contains a manifest.json is treated as a plugin.

Sites are declared in a site configuration file (JSON), passed to the runtime at startup:
 1. {
 2.   "sites": [
 3.     {
 4.       "id": "default",
 5.       "location": "./plugins"
 6.     },
 7.     {
 8.       "id": "npa.ui.tools",
 9.       "location": "./npa-ui-tools/src/plugins"
10.     },
11.     {
12.       "id": "apaf",
13.       "location": "./apaf/src/plugins"
14.     }
15.   ]
16. }
The runtime scans all sites in declaration order. When the same plugin id is found in multiple sites, the highest version wins. This allows downstream projects (like APAF) to override or upgrade individual NPA plugins without forking the entire repository.

The site config file path is resolved in this priority order:
  1. Environment variable APAF_INSTALLATION or NPA_SITE_CONFIG
  2. Command-line argument --installation or --site_config
  3. Default file ./appConfig.json in the working directory

Startup Sequence

  1. Load .env — environment variables from the env file (path overridable via ENV_FILE)
  2. Discover — scan all sites, parse every manifest.json via require()
  3. Resolve — check all requires entries; mark plugins with missing deps as unresolved
  4. Weight & Sort — compute topological weights, bubble-sort plugins ascending
  5. Lazy-load — for each resolved plugin in order: register extension points, then register extensions (lazzyPlug queued)
  6. Start Application — npa.core.startApplication(APPLICATION) triggers autostart services and calls the application plugin's start()
