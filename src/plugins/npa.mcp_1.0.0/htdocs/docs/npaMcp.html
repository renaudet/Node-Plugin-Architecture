npa.mcp — MCP Server Plugin

Overview

The npa.mcp plugin exposes a Model Context Protocol (MCP) server over HTTP using the Streamable HTTP transport. It listens on the same port as the NPA HTTP server (via npa.http) and registers all contributed tools at request time, making them available to any MCP-compatible AI client (VS Code, Claude, etc.).

Two endpoints are registered under /mcp:
  • POST /mcp/ — main MCP request handler (Streamable HTTP transport)
  • GET /mcp/health — health check, returns { "status": "ok", "server": "<name>" }
The server name is configured via the MCP_SERVER_NAME environment variable (defaults to npa-mcp-server).

Extension Point: npa.mcp.tool

Any plugin can contribute MCP tools by extending the npa.mcp.tool extension point in its manifest.json. Two contribution styles are supported.

Style 1 — API-descriptor (recommended)

This style wires an existing npa.http.handler extension directly as an MCP tool, using its embedded apidoc OpenAPI descriptor. No extra code is needed in plugin.js. Step 1 — add an apidoc field to the npa.http.handler extension:
 1. {
 2.   "point": "npa.http.handler",
 3.   "id": "my.plugin.myAction.handler",
 4.   "router": "my.plugin.router",
 5.   "method": "POST",
 6.   "schema": "/myAction",
 7.   "handler": "myActionHandler",
 8.   "apidoc": {
 9.     "paths": {
10.       "/myAction": {
11.         "post": {
12.           "operationId": "myToolName",
13.           "description": "What this tool does",
14.           "requestBody": {
15.             "content": {
16.               "application/json": {
17.                 "schema": {
18.                   "type": "object",
19.                   "required": [ "name" ],
20.                   "properties": {
21.                     "name": { "type": "string", "description": "Name of the item" },
22.                     "active": { "type": "boolean", "description": "Filter by active status" }
23.                   }
24.                 }
25.               }
26.           }
27.         }
28.       }
29.     }
30.   }
31. }
Step 2 — add the npa.mcp.tool extension referencing that handler by its id:
 1. {
 2.   "point": "npa.mcp.tool",
 3.   "id": "my.plugin.myAction.mcp.tool",
 4.   "apiId": "my.plugin.myAction.handler"
 5. }
At startup, npa.mcp resolves the handler extension by its apiId, extracts the apidoc descriptor, builds the Zod input schema, and registers a tool named after operationId. When the tool is invoked by an AI client, the original handler function on the contributing plugin is called directly — no extra HTTP round-trip.

Style 2 — Registrar function (advanced)

For tools that need full control over the MCP server.tool() call (e.g. streaming, dynamic schema), a registrar function can be declared directly in plugin.js:
 1. // manifest.json
 2. {
 3.   "point": "npa.mcp.tool",
 4.   "id": "my.plugin.custom.mcp.tool",
 5.   "registrar": "registerMyTools"
 6. }
 1. // plugin.js
 2. plugin.registerMyTools = function(server, httpReq) {
 3.   server.tool(
 4.     'myCustomTool',
 5.     'Does something custom',
 6.     { input: z.string().describe('The input value') },
 7.     async (args) => {
 8.       return { content: [{ type: 'text', text: 'result: ' + args.input }] };
 9.     }
10.   );
11. };
The registrar function receives the McpServer instance and the original HTTP request object (with headers) — useful to forward authentication tokens to downstream calls.

Supported apidoc Parameter Types

The apidoc field follows the OpenAPI 3.x structure. The following JSON Schema types are mapped to Zod:
JSON Schema typeZod type
stringz.string()
booleanz.boolean()
integer / numberz.number()
arrayz.array(z.any())
object with propertiesz.object(...).passthrough()
object without propertiesz.union([z.record(...), z.string()])
enum values arrayz.enum([...])
Fields listed in required are mandatory; all others are .optional(). Fields with a description property have it forwarded to the Zod schema via .describe(), which improves tool discoverability for AI clients. Structured object schemas keep their nested properties and required definitions when converted to Zod.

Parameter Routing

When using the API-descriptor style, arguments passed by the AI client are grouped into explicit top-level sections before being routed to the handler's req object:
  • Path parameters declared with "in": "path" are grouped under params and forwarded to req.params
  • Query parameters declared with "in": "query" are grouped under query and forwarded to req.query
  • The HTTP requestBody schema is exposed under a top-level body object and forwarded to req.body
For example, a handler with one path parameter and a JSON request body is exposed to MCP clients with an input payload shaped like:
 1. {
 2.   "params": { "id": "123" },
 3.   "body": { "name": "example" }
 4. }

Telemetry

Two telemetry dimensions are pushed every 30 seconds:
  • mcp.invocation.count — cumulative total number of MCP requests received
  • mcp.concurrent.clients — peak number of concurrent active clients since last collection
